2、必需的文件以及定位：

已发现的实验现象：用来记录每一次实验所发现的现象以及问题

论文素材库：记录每一次实验中有哪些现象值得写到论文里

论文笔记：记录每一篇论文的核心任务 方法架构 关键贡献 实验结果 与自己实验的关系 论文中发现的现象 核心方法的优缺点 可借鉴的内容 核心总结等内容

index：记录该项目所有文档及定位

最新实验分析报告：用来记录最近的实验报告

version\-evolution：记录项目的关键决策 方向调整

paper\-plan：记录当前项目从做实验到写完论文的宏观规划

experiment\-results：记录所有实验的详细数据

论文写作\-新会话读取清单：统计有哪些文档是可以辅助写论文

3、可选的文档

顶会论文创新思路分析：批量分析所有的顶会论文推理链总结出来的文档

顶会论文完整解题思路：批量分析所有的顶会论文从发现问题到提出解决方案经历了哪些步骤

所有论文创新类型全景分析：统计所有论文的创新方式，什么创新才能被顶会接收

顶会论文完整规律汇总：分析所有顶会论文的论文每一个章节都是怎么写的

顶会论文工作量分析：统计每一篇论文基于baseline都改进了几个模块

所有论文在baseline骨架的改进内容：统计所有的论文分别都在baseline的哪里做了改动以及改了什么

baseline骨架的全景图：记录当前对于baseline的不同结构的已了解内容和未知信息

外部工具应用现状：记录所有论文都是用了哪个领域的外部工具解决了什么问题



二、复现论文

baseline的选择方法：尽量选择近两年引用量最高的论文作为baseline，一是引用量高大概率有源码链接，二是一定有很多论文是基于这个baseline改进的，方便后续的制造意外实验



三、制造意外实验

1、使用mineru对pdf版论文解析为md论文，mineru的用法及介绍这里就略过了

2、调用analysi\-paper这个skill来对论文原文进行分析，并输出一份论文笔记

3、调用deep\-read skill来批量分析所有的论文原文，输出一个问题\-现象的交叉矩阵，核心逻辑是论文a的问题能否被论文b的现象解决。根据这个矩阵来进行不同方案之间的组合实验

4、调用squeeze\-experiment skill来尽可能的榨干实验数据价值并输出一份实验报告，同时将发现的现象更新到已发现实验现象文档



四、深挖意外现象

分析实验报告所发现的实验现象，对这个实验现象走1a\-2b的分析流程，反复多次的进行1a\-2b分析，最终就可以定位到这个现象的根因



五、构建baseline骨架全景图和所有论文在baseline骨架大改进地方以及改进内容

这两个文档的作用已在第一部分内容描述，通过交叉分析这两个文档，可以明确得知该骨架有哪些地方被多次改造，已经改烂了，还有哪些地方改造的次数比较少甚至从未有人改造过。

这里要注意一个点：

某个地方被改造的多只能说明这里存在有很大的问题，不能说明这里没有创新空间了

同理，如果一个地方完全没有被改造过，那么这里大概率没有问题需要改造，所以这里很可能是无解的地方，无论如何深入研究都找不到改进内容



通过不断的走第三步和第四步的流程，应该会对baseline的了解越来越透彻，也积累了非常丰富的实验现象，这时候只要找到一个最容易突破的实验现象，开始尝试解决这个问题，解决后实验阶段的流程就走完了



附录：

一、1a\-4b的完整流程

1a：观察所有失败实验的现象

1b：把所有发现的现象进行归类，查看有哪些现象指向了同一个根因

2a：对1b流程归类后的现象进行不断追问，尝试发现更深层次的原因

2b：对2a的追问结果建立一个因果链，逐层描述当前现象的问题所在

3a：替换掉2b中找到的某个有问题的模块尝试验证是否有效

3b：如果含有多个改动替换内容，那么所有的改动应该是独立互不影响的改动

4a：走完阶段三后开始消融，逐个添加模块验证单模块效果并量化每个模块带来的收益

4b：再次验证阶段三的改动是否符合阶段二所描述的问题分析

如果在某一个阶段的数据不理想，那么应该回退到上一个阶段重新走一遍流程，只有对上一个阶段几乎做到完全了解才可以进入下一个阶段

二、a\-d级论文定位

a级：提出问题并用新颖的方案解决问题

b级：用新颖的方案解决已知问题

c级：其他论文中提到的方案直接应用到自己的论文中

d级：仅对已有论文进行微调

三、a\-b级创新方法论

a级：通过现有系统做了一个意料之外的事情，不断追踪验证这个现象，即可发现一个全新的问题。

b级：该领域所面临的问题在别的领域也存在，那么可以去借鉴别的领域是如何解决这类问题的

## 论文读完不会用？5个Skill 打通科研全流程

你是否遇到过这些研究痛点？

- 论文读完只记住摘要，却说不清它真正解决了什么问题？

- 看了很多文献，却无法把零散信息连接成研究空白？

- 有了一个想法，却没有清晰的假设、对照和验证方案？

- 实验做完只保留一个最好看的数字，过程和异常都丢失了？

- 结果出现了新现象，却没有继续挖掘，下一步又回到盲目试错？

analyze‑paper、deep‑read、discover‑innovation、record‑experiment 和 squeeze‑experiment，就是为解决这些断点而设计的一套通用研究工作流。它们适用于不同学科，也适用于计算实验、实验室研究、临床研究、调查、模拟和工程测试。

我已经把这些skill放到了主页群聊里，有需要的可以自取。

一、Analyze Paper：真正读懂一项研究

这是流程入口。它不仅总结论文内容，还会核对研究问题、研究设计、样本或材料、测量与分析方法、主要结果、证据位置和结论边界，并区分作者主张、直接证据、分析推断与未知事项。

它的产出是 ANALYSIS\_PACKAGE，为后续矩阵分析提供可靠的研究事实，而不是直接把论文包装成创新点。

二、Deep Read：找到问题与现象的深层连接

deep‑read 目前只支持 Mode C。它把多篇论文、实验记录或其他研究材料中的问题 P、现象 F、机制 M 和证据 E 放进交叉矩阵，检查对象、条件、替代解释和证据强度。

它的产出是 MODE\_C\_PACKAGE，包括 P/F/M/E 清单、P×F 矩阵和候选连接点 C，帮助研究者从可靠证据出发寻找研究机会。

三、Discover Innovation：把连接点变成可检验想法

discover‑innovation 消费 MODE\_C\_PACKAGE，从一个明确的 C 连接点出发，形成研究假设、可观察预测、基线、对照、主要指标、重复方式、资源预算和结果解释规则。

它的产出是 IDEA\_PACKAGE，是一张可以真正交给执行者的 Idea 卡片，而不是一句模糊的“尝试新方法”。

四、Record Experiment：记录真实发生了什么

record‑experiment 负责记录完成或部分完成的实验、运行、调查、模拟和工程测试。它保存计划设计、实际配置、样本或材料、版本、所有运行、原始证据、结果、不确定性、异常和执行偏差。

它还区分“观察到的事实”“当前解释”和“待复验假设”，最终形成 EXPERIMENT\_RECORD，为后续深挖提供完整事实基础。

五、Squeeze Experiment：从一次实验中榨取更多知识

squeeze‑experiment 消费 EXPERIMENT\_RECORD 及其原始证据，分析主要结果之外的过程动态、错误模式、子组差异、边界条件、机制线索和稳健性。

它的产出是 SQUEEZE\_REPORT。结果不理想、没有明显差异或出现异常，也可以转化为限制、替代解释、待复验问题和新的研究线索。

六、组合使用后的效果

五个 skill 的调用顺序是：

```Plain Text
Analyze Paper
→ Deep Read（Mode C）
→ Discover Innovation
→ 实际执行实验
→ Record Experiment
→ Squeeze Experiment
→ 回流 Deep Read（Mode C）
```

它们共同形成一个“从证据到发现、再从发现回到证据”的闭环：先读懂已有研究，再建立问题—现象—机制联系；把联系转化为可检验方案；完整记录实验事实；从结果中提取更多信息；最后将新问题、新现象和新机制线索重新放回矩阵。

组合后的核心价值是：让研究更可追溯、更少依赖直觉和最佳结果，也让每次实验即使没有达到预期，仍然能够沉淀边界、机制线索和下一步问题，持续推动研究向前发展。



## 科研遇到问题后，怎样做实验才能少走弯路？

实验指标还是不动，我明明找到了问题根因，也设计了能解决当前问题的方案。连续两三天之后，我才开始追问：问题到底卡在哪？

发现问题 → 分析根因 → 设计解决方案 → 实验验证 → 发现新问题 → 再设计解决方案。

### 一、能解决问题，不代表能提升模型性能

做实验时，我们很容易这样想：模型出现了问题 A，就设计方案 B 去解决。只要能从理论上讲通 B 为什么有效，我们就觉得值得一试。

改方案时，我们通常先看它能带来什么收益，却很难提前看清它对系统其他部分的影响。一个新机制可能修好眼前的缺陷，也可能改变模型其他部分的行为，带出新的问题。

局部问题解决了，整体指标却没动，甚至下降。看到新问题后，我们又设计新方案去修，循环就接着往下走。

### 二、为什么知道根因，还是避免不了？

根因分析看的是已经发生的现象；设计方案时，我们却要估计还没发生的影响。

一个方案在理论上讲得通，不代表它的副作用也能提前算出来。复杂模型里，一个变量的改动还会影响其他因素，我们未必看得全。

AI 也一样。它能根据已有知识提出改进思路，却不能可靠预测所有变量关系。方案理论上成立，实验也未必能得到收益。

### 三、局部问题解决了，整体性能就会提升吗？

这几天的实验让我发现，我以前把两件事混在了一起：解决眼前的问题，和提升整个模型的性能。前一件做成了，后一件未必会跟着发生。

一个方案可能解决当前问题，也带来局部收益。可如果它同时造成其他性能损失，局部收益就可能被抵消，整体指标还是没有改善。

指标没涨，不能直接证明新机制一定弊大于利。评估噪声、变量交互也可能影响结果；至少这次，局部修复还没有转化成我们想要的整体收益。

### 四、设计方案还得算代价

科研实验难的地方之一，是判断局部修复能不能给整个系统带来净收益。解决方案本身，也可能成为新问题的来源。

如果每次遇到问题都增加一个新机制，模型可能越来越复杂，性能却没有改善。设计方案时，我们还得多问一句：为了解决这个问题，整个系统要付出什么代价？

副作用不可能都提前预测。面对一个已经明确的问题，实验该怎么设计，才能少几轮反复试错？这个问题我准备下一篇接着聊。



## 科研死循环的根本原因

上一篇文章，我讲了自己连续两三天陷入的科研死循环。它大概是这样：发现问题 → 设计方案 → 解决当前问题 → 引入新问题 → 再设计方案。

后来我发现，真正需要调整的，可能不是我提出 idea 的能力，而是我面对问题时的实验思路。方案不一定每次都有效，但实验不能只留下一个“没效果”。它至少应该告诉我，下一步要排除什么。所以我先把目前想到的几条做法列出来。

### 一、遇到问题，先别急着自己设计方案

以前遇到一个问题，我的第一反应往往是分析根因，然后让 AI 帮忙思考有没有办法解决。但无论是自己还是 AI，设计方案时都容易围绕当前问题寻找解决办法，很难准确预测新机制对整个系统的影响。所以我现在更倾向于先找有没有论文研究过类似的问题，优先分析其中的解决方法、实验结果和适用条件。

自己从零设计方案时，往往只能根据理论推测它是否有效；已有论文中的方法，至少在特定实验环境下经历过验证。这不代表照搬就一定有效，也不代表它没有负面影响，但能提供参考，降低试错成本。

### 二、一次尽量只改变一个变量

假设我提出一个新方案，里面包含 A、B、C 三个改动。如果一次性全部加入模型，最终实验指标提升了，我其实无法知道到底是哪个改动带来了收益。如果指标下降了，同样无法确定究竟是哪一个改动造成的。更麻烦的是，如果我继续在此基础上增加 D、E，那么实验结果只会越来越难解释。

只要能拆开验证，我就会一次只改一个变量。先验证 A 的效果，再验证 B，最后根据结果决定是否需要组合。

这样至少能回答一个问题：最终指标变了之后，我能知道究竟是哪一个改动带来了收益。当然，如果两个变量本身存在很强的交互作用，单独验证并不能揭示它们组合后的全部效果。实验刚开始时，先把变量拆开，后面的分析会轻松很多。

### 三、不要只关注想提升的那个指标

我们设计一个方案时，通常都有明确的目标。比如希望改善模型某个模块的表现，或者解决某个已经发现的问题。但如果实验结束后只检查这个问题有没有改善，就很容易忽略其他方面的变化。因此实验前，我会先写清楚：这个方案预计改善什么？哪些指标可能受到影响？最后看哪个整体指标，才能决定这个方案要不要留下？

不能因为局部问题得到了改善，就直接认定整个方案有效。如果局部收益明显，但整体指标没有改善，就应该继续分析收益为什么没有传递到最终结果上，而不是立刻再设计一个新方案去解决新出现的问题。

### 四、学会及时回退，而不是不断打补丁

最近几天的实验让我最警惕的，就是这一点。一个方案花了很多时间才做出来，很容易冒出一个念头：既然它已经解决了当前问题，那就应该继续优化，把新出现的问题也解决掉。可问题是，每补一个新机制，都可能再带出新的影响。于是原本只是想解决问题 A，最后却引入了 B、C、D。

具体来说，新加一个机制时，我会先问三个问题：它要解决的到底是哪一个问题？如果它没有改善整体指标，最迟在什么结果出现后回退？回退之后，哪些观察值得单独保留？这三个问题能把“继续补丁”变成一次有边界的实验。

如果系统越来越复杂，但整体指标始终没有提升，就应该考虑回退。当然，如果它提供了重要的新发现，也值得记录和进一步研究。但不能仅仅因为已经投入了很多时间，就不断增加机制试图挽救它。有时候，及时停止一个无效方向，比继续提出三个新方案更重要。

### 五、让每一次实验都有明确的结论

以前我容易把实验的目标理解为：看看这个 idea 能不能提升指标。现在我更想在每次实验前先说清楚一个问题，例如：这个改动能否独立改善目标指标？如果局部指标改善了，整体收益是否同步增加？如果没有改善，是核心假设不成立，还是存在其他因素干扰？

实验开始前，我还会先写下：什么结果算成功，什么结果出现后就该停。这样即使结果是负的，也不会只剩一句“没涨”。

一次实验当然不可能把所有原因都说明白。可在上一次结果还没弄明白之前，我不想再急着改下一版。

### 六、回头看

这几天反复试错后，我越来越觉得，做科研不能只看自己提了多少 idea，也不能拿实验次数当进度条。一天试五个方案，看起来很勤奋，但我更想通过一次实验，弄清楚一个方案为什么有效，或者为什么无效。

我现在更在意的，不是一次实验能不能带来提升，而是它结束后，我到底多知道了什么。失败本身不吓人，最浪费时间的是做完以后，连下一步该怎么走都说不清。

不过，控制变量和实验归因只解决了第一层问题：我可能知道问题出在哪，却还是不知道怎样设计真正有效的解决方案。从零设计的新机制，仍然可能带来预料不到的副作用。既然如此，能不能先看看其他领域有没有人解决过类似的问题？如果找到了，能不能不只是照搬模块，而是先搞清楚它为什么有效，再通过改造自己的 Baseline，让这个方法在自己的领域中发挥作用？

这正是我最近在整理的科研思路。下一篇就来聊聊，如何把其他领域论文中的解决方法迁移到自己的研究方向，而不是简单地把不同论文的模块缝合在一起。

## 跨领域论文方法迁移

上一篇我讲了科研中的死循环：发现问题，设计方案，解决当前问题，又引入新的问题，最后继续修改模块、调整参数，模型越来越复杂，指标却没有提升。

那篇文章最后留下了一个问题：如果从零设计新机制本身就容易带来副作用，能不能先看看其他领域有没有人解决过类似的问题？

这篇文章想讨论的，不是怎样把另一个领域的模块直接搬进自己的模型，而是先弄清楚它为什么有效，再改造自己的 Baseline，让这个作用机制在自己的研究任务中成立。

> 一个方法在其他领域有效，并不代表它在自己的领域也能直接生效。
> 
> 

下面这套流程是我拼接跨领域方法时采用的思路。

### 一、先把自己的问题挖到足够深

在寻找其他领域的方案之前，首先要确定自己究竟需要解决什么。这里可以沿用我之前 Day14 介绍的 1a\-2b 分析流程：

```Plain Text
1a：观察失败实验中出现的现象。
1b：对这些现象进行归类，寻找它们可能指向的共同根因。
2a：针对归类后的问题不断追问，寻找更深层的原因。
2b：把分析得到的原因串联成因果链，逐层解释问题是如何产生的。
```

但走完一次 1a\-2b，并不意味着分析已经结束。

应该继续追问 AI：当前分析得到了哪些新发现？这些发现中还有哪些值得继续研究的问题？

然后针对新发现，再走一遍 1a\-2b。

不断重复这个过程，尽可能把问题从表面现象深入到具体模块、运算机制，甚至算子层面。

当然，AI 给出的因果解释仍然需要结合代码、实验现象验证，不能把推测直接当成根因。

只有把问题落到具体机制，检索才不会停留在宏观任务关键词上，也才有可能跳出当前研究领域，找到解决同类底层问题的方法。

### 二、让 AI 批量寻找领域 B 的解决方案

明确问题后，让 AI 检索：

> 在其他研究领域中，是否已经有人遇到并解决了相同或相似的底层问题？
> 
> 

这里要区分的是：我们需要寻找的不是研究任务相同的论文，而是解决问题的机制相同或相似的论文。

即使两篇论文研究的任务完全不同，也可能面临同一种底层困难。

所以检索时，应该尽量使用前面分析得到的底层问题及机制描述，而不是仅仅使用自己领域的任务关键词。

找到候选论文之后，还需要核对原文，确认它确实研究了这个问题，而不是仅仅在摘要或者介绍中出现过类似的概念。

### 三、深入分析领域 B 的方法为什么有效

找到领域 B 的解决方法后，先不要急着将它加入自己的 Baseline。

应该先弄清楚三个问题：

1. 这个方法最初是为了解决什么问题？不能只知道它能够提升某个指标，还应该理解它针对的是哪一种具体机制或缺陷。

2. 它究竟通过什么机制解决了问题？需要深入到方法的核心结构，分析真正产生效果的是哪一部分。

3. 这个方法需要哪些条件才能生效？例如，它是否依赖某种输入特征、数据分布、模型结构或训练目标？如果这些条件不存在，方法是否仍然能够发挥作用？

我认为第三个问题尤其重要。

因为一个方法在领域 B 有效，可能恰恰是由于领域 B 天然具备某些条件，而自己的领域 A 未必满足这些条件。

> 如果没有弄清楚生效条件，那么所谓的跨领域迁移，很可能只是把一个模块机械地搬到另一个模型里，同时很难取得预期效果。
> 
> 

### 四、寻找领域 C，研究别人是怎么迁移的

理解领域 B 的方法之后，再让 AI 进一步检索：

> 有没有其他领域 C，已经将领域 B 的方法应用到了自己的研究任务中？
> 
> 

之所以还要寻找领域 C，是因为领域 B 只能告诉我们，这个方法在原始环境下为什么有效，而领域 C 可以提供另一个重要参考：当研究任务、模型结构发生变化后，这个方法究竟需要怎样改造才能被应用？

这里需要重点对比领域 B 和领域 C：

- 领域 C 是直接使用了原方法，还是修改了输入输出结构？

- 是否调整了网络连接方式、训练目标或者其他机制？

- 这些改造中，哪些是为了适配任务，哪些可能是方法能够发挥作用的必要条件？

通过对比这两个领域，我们就有机会进一步区分：

> 一个方法真正不可缺少的生效条件是什么，又有哪些只是原始论文中的具体实现方式。
> 
> 

当然，没有找到领域 C，也不代表方法不能迁移；只是缺少现成的迁移案例，后续需要承担更多验证工作。

### 五、不是把方法塞进 Baseline，而是改造 Baseline 来适配方法

前面几步完成后，我们至少应该能够回答：

```Plain Text
领域 A 存在什么问题？
领域 B 使用什么机制解决了类似问题？
这个机制需要哪些条件？
领域 C 又是如何将这个机制迁移到其他任务中的？
```

回答完这些问题，方案设计还需要换一个方向来想。

以前我们可能会想：

> ~~怎样修改领域 B 的方法，让它能够直接加入领域 A？~~
> 
> 

实际上应该思考：

> 能不能通过改造领域 A 的 Baseline，使它具备领域 B 方法发挥作用所需要的条件？
> 
> 

比如，原方法需要某种特定形式的输入，但当前 Baseline 无法提供。那么首先需要考虑的，就不一定是修改原方法本身，而是能否改造 Baseline 的某部分结构，让它产生符合要求的输入。

这才是我认为更值得研究的跨领域迁移方式。

我们不再只是关注如何把两个模块连接起来，而是研究如何让原方法的作用机制在新系统中成立。

### 六、最后还需要验证，到底是谁带来了收益

结构改造完成后，还要把“适配带来的收益”和“方法本身带来的收益”拆开验证：

```Plain Text
Baseline A：原始 Baseline
Baseline A'：只进行结构适配
A'+B：结构适配后再加入领域 B 方法
```

Baseline A 与 A' 的差异，说明结构适配本身是否有效；A' 与 A'\+B 的差异，才说明领域 B 方法在新系统中是否继续带来收益。同时还要观察目标问题是否改善，以及整体指标是否稳定提升；单看最终指标的偶然提升，仍不足以证明迁移机制成立。

### 七、最后

跨领域借鉴的重点，不是看到某个方法有效，就想办法把它加入自己的模型，而是先理解它为什么有效，以及它需要什么条件。

所以整套流程可以概括为：

```Plain Text
发现领域 A 的问题
  -> 深挖根因
  -> 寻找领域 B 的解决方案
  -> 分析方案的生效条件
  -> 研究领域 C 的迁移方式
  -> 改造领域 A 的 Baseline
  -> 验证实际收益
```

它无法保证一定找到有效的 idea，但相比于随意组合不同论文中的模块，这种方式至少能让每一次迁移建立在更加明确的问题分析和机制假设之上。

> 跨领域迁移真正要搬过来的，从来不只是方法本身，而是让这个方法能够发挥作用的条件。
>
